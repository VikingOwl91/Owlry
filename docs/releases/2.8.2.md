# Owlry 2.8.2

Owlry 2.8.2 moves every launched app into its own systemd user scope, so apps
no longer share owlry's scope in monitoring, `systemd-cgtop`, OOM handling, or
when the scope is stopped.

## What changed

With `use_uwsm = false` (the default), owlry used to spawn apps as direct child
processes. They inherited owlry's own scope (for example
`app-niri-owlry-<rand>.scope` under niri/uwsm), so Firefox, Steam, or Electron
showed up inside owlry's scope with gigabytes of memory attributed to owlry.

Every launch is now moved into its own transient scope
`app-owlry-<appid>-<rand>.scope` under `app-graphical.slice` via the user
manager's `StartTransientUnit`, the same mechanism uwsm and niri use. After a
launch, owlry's scope contains only owlry. The move costs one D-Bus roundtrip
and the process keeps its PID, so nothing about process handling changes.

Desktop entries without `DBusActivatable=true` and with a plain `Exec` line are
now spawned directly from the parsed argv, so the scoped PID is the app process
itself. `Terminal=true` entries launch in the configured `terminal_command`
(default `xterm`). D-Bus-activatable entries, and entries whose `Exec` is
shell-invoking or unparseable, still go through `gio launch` and get their own
unit from the user manager. When no systemd user manager is reachable (for
example a non-systemd session), apps are spawned directly as before. With
`use_uwsm = true`, behavior is unchanged: uwsm already creates
`app-uwsm-...` scopes.

## Upgrading

Update the Arch package normally:

```bash
paru -Syu owlry
```

Restart the daemon and the launcher UI after upgrading (`systemctl --user
restart owlry.service`, then relaunch the UI). You can verify the new behavior
with:

```bash
systemd-cgls --user
# launched apps appear as app-owlry-<appid>-<rand>.scope under app-graphical.slice
cat /sys/fs/cgroup/user.slice/user-$(id -u).slice/user@$(id -u).service/app.slice/app-graphical.slice/app-niri-owlry-*.scope/cgroup.procs
# lists only the owlry UI process after launching apps
```
